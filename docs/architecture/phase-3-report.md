# Phase 3 — Workflow Core: отчёт

## Что сделано

**Формат и хранение.** Workflow сохраняется как `.mmflow` (JSON): граф, раскладка (позиции, свёрнутость, размеры узлов),
версия формата и `typeVersion` каждого узла. `WorkflowSerializer` терпимо читает файл и сообщает о потерях
(`WorkflowLoadResult.IsLossy`), цепочка миграций `WorkflowMigrator` поднимает старые файлы по одной версии формата.
`IWorkflowStore` / `FileWorkflowStore` — запись и чтение с диска.

**Проекты.** `ProjectService`: создать, открыть, сохранить (Ctrl+S), переименовать (в верхней панели и в списке), список проектов
в папке проектов (по умолчанию в данных приложения, папку можно сменить в настройках). У каждого проекта есть обложка
`Имя.cover.png` рядом с файлом: своё изображение или случайная абстрактная картинка (генерируется без внешних пакетов).

**Валидация графа целиком** (`GraphValidator`). Кроме проверок узлов (обязательные параметры, диапазоны, JSON, опции,
неподключённые обязательные входы) теперь есть правила всего графа:

| Правило | Код | Уровень |
|---|---|---|
| нет ни одного включённого триггера | `GraphHasNoTrigger` | предупреждение |
| узел без единого соединения (если в графе больше одного узла) | `NodeNotConnected` | предупреждение |
| цикл в соединениях (в файле, правленном руками) | `GraphHasCycle` | ошибка |

`ValidationIssue.IsGraphLevel` отличает проблему графа от проблемы узла; `GraphValidator.IsRunnable` — «нет ошибок».
Предупреждения запуск не блокируют; блокировка будет решаться рантаймом (Phase 4).

**Операции изменения графа** (`MindMesh.Graph.Operations`). Изменения описываются данными, их можно хранить и передавать:
добавить/удалить узел, соединить/разъединить, задать параметр, название, «выключен», переместить.
`GraphOperationBatch` применяется **«всё или ничего»**: `GraphOperationApplier.Validate` находит все проблемы батча
(неизвестный тип, узел, порт, параметр, недопустимое соединение, неверный JSON) и ничего не меняет;
`Apply` выполняет проверенный батч как **один шаг undo**, а если команда всё же упала посреди выполнения — откатывает уже
выполненные. Узлы батча получают id от автора, поэтому в одном батче можно добавить узел и сразу соединить его.
`GraphOperationSerializer` пишет/читает батч в JSON (поле `op`), непонятный текст отвергает.

**Интерфейс (по списку пожеланий).** Горячие клавиши с переназначением, разделы настроек, темы с мини-превью,
галерея проектов с поиском и обложками на главном экране, оригинальная иконка приложения.

## Решения, принятые по умолчанию (можно пересмотреть)

- Предпросмотр операций (список «+1 узел, −1 соединение») не делался: достаточно «всё или ничего» + Undo.
  Предпросмотр логично добавить вместе с AI-ассистентом.
- Механизм миграции параметров узлов по `typeVersion` не делался: версия типа узла уже пишется в файл и читается,
  а миграции появятся при первом реальном изменении параметров узла.

## Не сделано / ограничения

- Проверка «есть триггер» опирается на категорию `Triggers`.
- `Validate` для операций не моделирует цикл, который создают два соединения одного батча: такой батч будет отвергнут
  при выполнении (с откатом), а не заранее.
- Операции пока не подключены к UI (их будет использовать ассистент и плагины).
- Рантайм, отладчик и запуск — Phase 4.
- Внешний вид UI проверялся только тестами и CI, не глазами.
